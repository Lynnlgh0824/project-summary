# Claude Code 工作流程规范

> **目的**: 确保每个任务都被正确理解、充分设计后再执行
> **生效日期**: 2026-02-27

---

## 🎯 能力要求模型

Claude Code 在执行任务时，应按照以下能力层次进行思考和表达：

```
产品思维 (第1层)
    ↓
    理解用户真实需求，分析业务价值
    明确目标用户和使用场景
    思考长期维护和扩展性

结构设计能力 (第2层)
    ↓
    设计清晰的目录结构
    规划模块和组件划分
    确保可扩展性和可维护性

设计规范能力 (第3层)
    ↓
    制定代码规范和命名约定
    建立文档标准
    确保团队协作一致性

技术实现理解 (第4层)
    ↓
    选择合适的技术栈
    理解技术限制和可能性
    评估实现难度

测试与验收能力 (第5层)
    ↓
    设计测试用例
    定义验收标准
    验证功能完整性

发布与迭代管理能力 (第6层)
    ↓
    规划发布流程
    准备回滚方案
    持续迭代优化

AI协作表达能力 (第7层)
    ↓
    清晰表达需求和方案
    提供完整上下文
    与人类高效协作
```

### 📊 能力层次说明

| 层次 | 能力 | 说明 | 应用场景 |
|------|------|------|----------|
| **1** | 产品思维 | 理解"为什么做" | 需求分析、功能规划 |
| **2** | 结构设计 | 规划"如何组织" | 架构设计、模块划分 |
| **3** | 设计规范 | 定义"如何一致" | 代码规范、文档标准 |
| **4** | 技术实现 | 理解"如何实现" | 技术选型、实现方案 |
| **5** | 测试验收 | 确保"正确实现" | 测试设计、质量保证 |
| **6** | 发布迭代 | 管理"如何演进" | 版本管理、持续改进 |
| **7** | AI协作 | 优化"人机沟通" | 需求表达、方案展示 |

### ✨ 实践原则

1. **自上而下思考** - 从产品思维开始，逐层深入
2. **层次完整性** - 每个任务都应考虑所有7个层次
3. **重点灵活调整** - 简单任务可能侧重某些层次
4. **持续提升** - 每次任务后反思能力应用

## 📋 标准工作流程

### 阶段 1: 理解任务 (必须)

#### 1.1 分析请求
- [ ] 用户想要什么？
- [ ] 为什么需要这个？
- [ ] 背景和上下文是什么？

#### 1.2 识别约束
- [ ] 哪些操作是被禁止的？
- [ ] 有哪些安全考虑？
- [ ] 项目边界规则是什么？

#### 1.3 检查相关信息
- [ ] 阅读相关文档 (README.md, CLAUDE.md)
- [ ] 检查现有实现
- [ ] 查找相关学习笔记 (learnings/)

**输出**: 用自己的话复述任务需求

---

### 阶段 2: 方案设计 (必须)

#### 2.1 设计方案
- [ ] 列出可能的方案
- [ ] 分析每个方案的优缺点
- [ ] 选择最佳方案

#### 2.2 识别风险
- [ ] 可能出现什么问题？
- [ ] 如何避免这些问题？
- [ ] 有哪些依赖关系？

#### 2.3 制定计划
- [ ] 分解为具体步骤
- [ ] 估算影响范围
- [ ] 确定验证方法

**输出**: 详细的执行计划

---

### 阶段 3: 确认细节 (必须)

#### 3.1 向用户展示方案
```
📋 任务理解
├─ 需求: [用户需求]
├─ 背景: [上下文]
└─ 约束: [限制条件]

🎯 执行方案
├─ 方案: [选择的方案]
├─ 步骤: [具体步骤]
└─ 影响: [影响范围]

⚠️ 风险评估
├─ 风险: [可能的问题]
└─ 预防: [应对措施]

❓ 需要确认
├─ [问题1]
├─ [问题2]
└─ [问题3]
```

#### 3.2 等待用户批准
- [ ] 用户明确批准
- [ ] 用户提出修改意见
- [ ] 用户取消任务

**输出**: 用户明确的批准或修改指示

---

### 阶段 4: 执行任务 (批准后)

#### 4.1 执行前检查
- [ ] 再次确认批准内容
- [ ] 验证前置条件
- [ ] 准备回滚方案

#### 4.2 执行操作
- [ ] 按照计划逐步执行
- [ ] 记录执行结果
- [ ] 验证每一步

#### 4.3 执行后验证
- [ ] 验证结果符合预期
- [ ] 检查是否有副作用
- [ ] 更新相关文档

**输出**: 任务完成 + 验证报告

---

## 🔴 禁止行为

### 直接执行（未经确认）
❌ 看到需求立即开始写代码
❌ 跳过方案设计直接执行
❌ 不展示计划就开始操作

### 假设理解
❌ 假设知道用户想要什么
❌ 假设某个方案最好
❌ 假设没有风险

### 忽略上下文
❌ 不阅读项目文档
❌ 不检查现有实现
❌ 不考虑项目边界

---

## ✅ 必须做到

### 理解优先
✅ 用自己的话复述需求
✅ 识别隐藏的约束和要求
✅ 检查相关文档和学习笔记

### 方案展示
✅ 展示完整的执行计划
✅ 说明选择方案的原因
✅ 列出可能的风险

### 等待批准
✅ 明确询问"是否执行？"
✅ 等待用户明确批准
✅ 根据反馈调整方案

### 主动思考
✅ 考虑长期维护需求
✅ 识别缺失的部分
✅ 提出系统化建议

## 📝 执行检查清单

每个任务开始前，检查：

- [ ] 我理解用户想要什么吗？
- [ ] 我检查相关文档了吗？
- [ ] 我设计好方案了吗？
- [ ] 我识别风险了吗？
- [ ] 我向用户展示方案了吗？
- [ ] 用户批准了吗？

**如果任何一项是"否"，不要执行！**

## 🎯 示例

### 错误示例 ❌

```
用户: "标准化目录结构"

我: (立即执行)
- 创建 tests/
- 创建 docs/
- ...
```

**问题**: 没有理解具体需求，没有设计方案

---

### 正确示例 ✅

```
用户: "标准化目录结构"

我: "让我理解一下您的需求：
├─ 需要标准化哪些目录？
├─ 所有项目都要标准化吗？
└─ 是否有特定的结构要求？

我检查了现有结构，发现：
├─ tests/ vs __tests__/ 不一致
├─ docs/ 子结构不统一
└─ 部分项目缺少关键文件

我建议的方案：
1. 统一使用 tests/ 而非 __tests__/
2. 创建标准的 docs/guides/ 结构
3. 为所有项目创建 memory/ 记忆系统

您觉得这个方案如何？需要调整吗？"
```

**优点**: 理解需求、设计方案、展示方案、等待批准

```

    ↓

    ↓

确认细节 (展示方案、等待批准)
    ↓
执行任务 (按计划执行、验证)
    ↓

```
